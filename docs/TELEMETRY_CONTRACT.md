# MELO Desktop ↔ Control Room Telemetry Contract

## Purpose

This document defines the boundary between MELO Desktop and the MELO Website Control Room. Desktop and Website remain separate projects/workflows; they communicate only through the telemetry API described here.

## Principles

- Telemetry is opt-in/controllable from MELO Desktop where appropriate.
- Never send Spotify OAuth access/refresh tokens, passwords, setup secrets, API keys, personal files, microphone/camera data, location, browser history, or unrelated user activity.
- Crash payloads must be sanitized before transmission.
- The server validates every field and applies rate limits.
- Installation IDs are opaque random identifiers generated by the Desktop client; never derive them from hardware serials, usernames, or other sensitive identifiers.
- Timestamps are UTC Unix seconds.

## Authentication

Desktop telemetry must use a dedicated server-issued telemetry credential/mechanism. It must **not** use the admin session cookie, admin TOTP secret, Cloudflare setup token, or any browser credential.

The exact credential mechanism will be implemented with the telemetry API. Do not hard-code a secret into the Desktop executable.

## Common envelope

```json
{
  "installation_id": "opaque-random-id",
  "event_id": "opaque-random-event-id",
  "event_type": "install | heartbeat | crash | version",
  "timestamp": 0,
  "app_version": "1.0.0",
  "build": "184",
  "platform": "windows",
  "os_version": "Windows 11",
  "client_schema": 1
}
```

## install

Sent when a new installation is registered.

Additional fields:

```json
{
  "event_type": "install"
}
```

The server records first_seen and installation metadata. No hardware fingerprint is required.

## heartbeat

Used to determine last_seen/active installations.

```json
{
  "event_type": "heartbeat"
}
```

The Desktop should not send heartbeats more frequently than the server allows. The server may discard excessive heartbeats.

## version

Sent after an application update or when the server needs current version information.

```json
{
  "event_type": "version"
}
```

The server uses this to calculate version adoption.

## crash

Crash reports are sanitized and minimal.

```json
{
  "event_type": "crash",
  "crash": {
    "error_type": "RuntimeError",
    "message": "sanitized error message",
    "stack_trace": "sanitized stack trace",
    "severity": "error"
  }
}
```

Before transmission, the Desktop must remove secrets, access tokens, filesystem paths containing usernames where practical, file contents, and unrelated personal data. The server must also enforce payload-size limits and sanitize stored output.

## Server-side records

The planned D1 model separates:

- `installations` — one record per opaque installation ID
- `telemetry_events` — normalized event/audit stream
- `crash_reports` — sanitized crash records
- `releases` — MELO production builds and rollout metadata
- `feature_flags` — server-controlled product flags

These records power the Control Room without coupling its UI directly to Desktop internals.

## Planned endpoints

- `POST /api/telemetry/install`
- `POST /api/telemetry/heartbeat`
- `POST /api/telemetry/version`
- `POST /api/telemetry/crash`

Admin endpoints remain separate under `/api/admin/*` and continue using the existing TOTP + server-side session authentication.

## Control Room mapping

- Dashboard → aggregate installations, active installations, versions, crashes, security/service health
- Users → only when a future legitimate account system exists; do not infer users from installation IDs
- Installations → installation metadata and last seen
- Crashes → sanitized crash reports
- Security → rejected/invalid telemetry requests, rate limits, auth failures
- Releases → release/build metadata and adoption
- Feature Flags → controlled feature configuration
- Analytics → aggregate telemetry only
- System Health → Worker/D1/API health

## Implementation order

1. Finalize this contract.
2. Create D1 tables and indexes.
3. Implement Worker telemetry endpoints with validation/rate limiting.
4. Add authenticated test requests without modifying MELO Desktop yet.
5. Connect MELO Desktop in its separate project.
6. Replace Control Room placeholder metrics with real D1 queries.
